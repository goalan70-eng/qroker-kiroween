# Task 7.2 robustness experiment: design, workload and timing plan

**Synthetic images, not real cameras.**

**A zero false-acceptance count is an observation, not a mathematical guarantee.**

Everything planned here, and every number the experiment will produce, concerns rasters drawn by `src/optical/` and `src/optical/testing/` and degraded by `src/optical/degrade.ts` with fixed seeds. They are synthetic-test findings about the sampled conditions only. They do not measure or guarantee real-camera performance, and the zero-event bound applies only to the sampled synthetic condition distribution (independent seeded trials).

This file is generated by `npm run robustness -- --plan` from `src/optical/testing/robustness-design.ts`. Its design parts are deterministic (no timestamps); the timing section is copied from `docs/optical/results/robustness-bench.json`, written by `--bench --write`. The sweep (tasks 7.2 execution and 7.4) writes `robustness.json` and `robustness.md`; they do not exist yet.

Every condition has at least 1,000 trials (checked by the tests). The two families are reported separately and never pooled; conditions are never pooled. The exact one-sided 95% bound for zero misidentifications is 0.30% for n = 1000, 0.15% for n = 2000, 0.03% for n = 10000.

## 2. What is simulated, what the reader gets, what is judged

**Flat family (A).** `composeGroup` of `group-compose.ts`: four markers around one vertex on a 32 x 32 module canvas, 4 px per module (128 x 128 px), white background, four distinct cards drawn per trial with a facing fragment in every slot (the generator of the task 5 group tests). The reader is `decodeGroup(image)` with its defaults.

**Physical family (B).** `buildScenario` / `renderScenario` of `geometry-trial.ts`: rounded cards of 63.5 x 88.9 mm on a dark table (gray 64), 4 px per module, faces, flips, registration and cut offsets, placement errors, 3x3 boards with Distractor_Markers (rejection-sampled so that exactly one interior vertex has four markers). The Milestone 5 camera chain is NOT used; the degradations of `degrade.ts` are applied on top of the composition. The reader is `decodeGroup(image, { centerOffsetModules })` where the offset (`inset + quiet margin + 3.5` modules) comes from the predefined layout parameter, never from identities or board state (the rule of task 5.6). Default acceptance radius r_acc = 1, position tolerance 1.0, marker-like gate and the frozen codebook (SHA256 `515ECEB318648C14A47574496788236A2B1BBDFC7062387DB09303CB717CC2D4`) are untouched.

**Judging.** The truth is used only after decoding. CORRECT = IDENTIFIED with exactly the right card set and sum. REJECTED = any other decoder kind (kinds are tallied). MISIDENTIFIED = IDENTIFIED with a wrong card set or sum, or IDENTIFIED for an incomplete composition (one card or marker absent, where the expected outcome is a rejection). Per condition the result files record n, correct count and rate, rejected count and rate with kinds, the misidentification count and rate, every misidentified trial (trial index and seed, reproducible), the first 10 non-expected rejections, and, only when the misidentification count is 0, the exact one-sided 95% bound 1 - 0.05^(1/n).

Experimental pass criterion: the observed misidentification count is 0 in every condition. Any observed misidentification marks the task failed-with-findings (failing seeds and conditions are recorded; thresholds are never loosened). A count of 0 is an observation in n synthetic trials, not a mathematical guarantee, and says nothing about real cameras. Success rates are measurements, not pass/fail. The mathematical guarantee (independent bit-flip model of design.md section 7, correction up to 2 bit errors, rejection of 2 to 3 bit errors for r_acc = 1) is a different statement from this finite-sample criterion; for arbitrary image corruption there is no guarantee.

## 3. The three error categories are distinct factors

| Category | What it is | Parameter(s) | Family | Implementation |
|---|---|---|---|---|
| 1. Fragment position error | image-space translation of the optical marker footprint by exactly 0, 0.1 or 0.25 module in a seeded uniformly distributed direction, one independent direction per marker | `fragmentModules` | A and B | `fragmentOffsets` / `shiftFragments` of `degrade.ts` (stage 0) |
| 2. Card placement error | physical movement of a whole card: seam shift, per-card rotation, unintended gap | `placementShiftMm`, `placementRotDeg`, `gapMm` | B | `buildScenario` / `renderScenario` (the 5.6 model of `seededErrors` / `composeBoard`) |
| 3. Duplex registration error | front/back printing misalignment (shift, rotation) and cut-outline offset | `regShiftMm`, `regRotDeg`, `cutOffsetMm` | B | `printLayers` / registration model of `physical-card.ts` as used by `geometry-trial.ts` |

The three categories share no parameter and are never relabelled (checked by `robustness-design.test.ts`). Fragment position error is never combined with category 2 or 3: it is applied to the footprint rectangles of the NOMINAL marker positions, which equal the true positions only when no card moves, and a moved card could otherwise be cut by the rectangle. The combined physical profiles with placement and duplex error therefore have fragment error 0, and the camera-only profiles (perfect cards) carry the fragment error.

## 4. Physical geometries permitted by the task 5.6 decision table

The decision table of `geometry-experiments.md` section 9 recommends NO corner-radius reduction (Requirement 15.7 allows it only after steps 1 to 4 are evaluated; steps 2 and 3 were not) and names no radius or inset candidate. Step 1 only reports one descriptive difference (r = 0 mm, STRESS, inset 2 lower than inset 1). Therefore family B uses the baseline only: **corner radius 3.175 mm, inset 1 module**, and no other radius or inset is included. ### Sub-pixel phase jitter

The Milestone 5 analysis found that cells with exactly 45 deg rotation, or without any warp, sample one pixel phase only, so their 0% and 100% results do not show robustness over phases. Every condition with any degradation therefore carries `phase = JITTER`: a seeded translation, uniform in [-0.5, 0.5) px per axis, is composed into the single geometric homography of the camera stage (perspective, rotation, translation; one resampling). It is the same as placing the scene on the canvas at a random sub-pixel offset. `degrade.ts` is not changed: `robustness-trial.ts` calls its exported `degrade`, `perspectiveMatrix` and `warpHomography`, and for a zero translation the result is byte-identical to `degrade` (tested). Conditions with `phase = EXACT` (the clean condition, 45E, 90E, 180E, 270E, and the physical conditions without a camera degradation) keep the exact lattice on purpose; the exact 45 deg conditions are kept next to the jittered ones so that the two can be compared. Axis-aligned conditions without jitter sample one pixel phase by construction (physical conditions without a camera effect still vary through the seeded card errors).

### Combined profiles (design choices, defined once)

| Profile | Definition |
|---|---|
| CLEAN | no degradation, exact lattice |
| MILD | fragment error 0.1 module, random rotation, tilt 10 deg, blur 0.5 px, noise sigma 5, illumination 0.2 |
| MODERATE | fragment error 0.25 module, random rotation, tilt 20 deg, blur 0.5 px, noise sigma 10, illumination 0.4 |
| STRESS | fragment error 0.25 module, random rotation, tilt 30 deg, blur 1.0 px, noise sigma 20, illumination 0.6 |
| ALIGN-MILD (B only) | placement shift 0.5 mm, card rotation 1 deg, gap 0; registration 0.25 mm, 0.5 deg, cut offset 0.5 mm; camera MILD without fragment error |
| ALIGN-MODERATE (B only) | placement shift 1.0 mm, card rotation 1 deg, gap 0.5 mm; registration 0.5 mm, 0.5 deg, cut offset 0.5 mm; camera MODERATE without fragment error |

MILD and MODERATE reuse the tilt / blur / lighting levels of the task 5.6 profiles MODERATE and STRESS and add noise and fragment position error; STRESS extends them to levels at which the single-factor sweeps already lose trials. The ALIGN profiles pair the 5.6 placement and registration levels with the matching camera profile.

### Pilot disclosure

Before the plan was frozen, 30 trials of each of the 82 explicit flat conditions were run with pilot seeds disjoint from the sweep seeds (`trialSeed('pilot:<id>', i): seeds disjoint from the sweep`; the counts of the final design are in `robustness-bench.json`, `flatPilot`): 26 conditions all correct, 19 all rejected, 37 mixed; misidentifications seen in the pilot: 0. An earlier run of the same pilot (not stored, it was repeated after the change below) found exactly one design problem: with the camera distance of 1.0 image diagonal every flat trial at 30 deg tilt was rejected, because the flat canvas (45 modules diagonal) is much smaller than a board image (146 modules for 2x2), which makes the perspective across a marker about four times stronger. The flat camera distance was changed to 4 diagonals (the same distance in modules as the physical family) and nothing else was changed: no level, profile, threshold or tolerance was tuned to the results. The three flat STRESS conditions had 0 of 90 pilot trials correct; the profile is kept as defined (it was fixed before the pilot), because a profile that is mostly rejected still tests that the reader rejects instead of guessing. No physical pilot was run besides the 20 timing trials per cost class (outcomes in `robustness-bench.json`).

The **randomized mix** conditions are supplementary: each trial draws every factor independently and uniformly from its level set (rule in `resolveParams`), which samples the full cross product without enumerating it. A mix is ONE condition with its own n and bound; it never stands in for the explicit conditions and its counts are never added to other conditions. They can be removed from the design by deleting six lines of `buildConditions` without touching anything else.

### Full factorial for comparison, and why it is not run

Family A (flat): complete / incomplete group 2 x fragment position error 3 x camera rotation setting (13 fixed + random) 14 x perspective tilt 6 x blur 5 x noise 6 x illumination gradient 5 x reflection 3 = **226,800 conditions**, 226,800,000 trials at the minimum of 1,000.

Family B (physical): board layout 2 x complete / incomplete group 2 x face x flip x registration shift x registration rotation x cut offset (distinct) 75 x placement shift 4 x placement rotation 4 x gap 3 x fragment position error 3 x camera rotation setting (0 exact, 0 jitter, 45 exact, 45 jitter, 90, 180, 270, random) 8 x perspective tilt 5 x blur 5 x noise 6 x illumination gradient 5 = **259,200,000 conditions**, 259,200,000,000 trials at the minimum of 1,000.

At the measured 7.4 ms per flat trial and 112 ms per physical 2x2 trial the full factorials need about 19.4 days (A) and 922 years (B) of single-process time, so the stratified design below is the only feasible one.

## 8. Seeds and reproduction

Seed of trial i of condition `id`: `trialSeed(id, i)` = 32-bit hash (FNV-1a with the MurmurHash3 finalizer, `hash32` of the geometry experiment) of the text `20260601|<id>|<i>`, a pure function of (base seed, condition id, trial index). Random streams of one trial are derived with `streamSeed(seed, stream)`: cards (1), placement and duplex errors (streams 2 and 3 of `buildScenario`), camera angle / tilt axis / lighting direction (11), sub-pixel phase (10), randomized-mix draws (12), and the master seed of the `degrade` stages (13), whose fragment and noise streams are `stageSeed(master, ...)`. Conditions are independent draws and are not paired. Example: trial 0 of `A-CLEAN` has seed 86926908.

Re-run one trial (for example a failing one): `npm run robustness -- --repro --cell <condition id> --trial <trial index> [--image out.png]`. It prints the seed, the resolved parameters (the drawn ones for a mix), the decoder result class and kind, and optionally writes the decoder input image. Results do not depend on sharding or the number of processes.

### Feasibility

Recommended design (this plan): **263 conditions, 363,000 trials, 8.28 h single process, about 2.24 h with 4 processes, about 1.42 h wall time with 8 processes** (measured speedup 5.81).

Larger variant for comparison (every ordinary physical condition at n = 3000, so the bound is 0.10% instead of 0.30%): 713,000 trials, 23.30 h single process, about 4.01 h with 8 processes.

The recommended design is within about 3 hours of wall time at 8 processes, so no reduced design is needed to stay inside that budget; every required level appears in explicit conditions and no condition is below 1,000 trials.

## 10. Recommended launch procedure

1. Check the machine: `Get-Process | Sort-Object CPU -Descending | Select-Object -First 8` and the CPU counter. Do not run `npm run test:ci` during the sweep (the load-sensitive 5 s tests of `detect.test.ts` and `physical-card.test.ts` time out under saturation).
2. Smoke test: `npm run robustness -- --run --max-trials 5 --work-dir .robustness-smoke` then `npm run robustness -- --merge --allow-partial --work-dir .robustness-smoke --out-dir .robustness-smoke/out`. Never write smoke data to `docs/optical/results` (the merge step refuses).
3. Family A (minutes): create the log folder (`New-Item -ItemType Directory -Force .robustness-work/logs`), then start 8 shards, for example `0..7 | ForEach-Object { Start-Process -NoNewWindow npx.cmd -ArgumentList "tsx scripts/run-robustness.ts --run --family flat --shard $_/8" -RedirectStandardOutput ".robustness-work/logs/flat-$_.txt" }`.
4. Family B: the same with `--family physical`. Shards are cost balanced (greedy by trials x class weight); each writes disjoint files to `.robustness-work/physical/<id>.json`. A restarted shard skips finished conditions, so an interruption loses at most one condition per shard.
5. Merge: `npm run robustness -- --merge` writes `docs/optical/results/robustness.json` and `.md` (deterministic, sorted by plan order, no timestamps). Exit code 2 when the data set is incomplete.
6. Keep the console output of each shard next to the results (task 7.4).
