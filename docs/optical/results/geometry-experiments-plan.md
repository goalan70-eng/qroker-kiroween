# Task 5.6 geometry experiments: design, workload and timing plan

**Synthetic images, not real cameras.** Everything planned here, and every number the experiment will produce, concerns rasters drawn by `src/optical/testing/` and sampled with fixed seeds. These are synthetic-test findings about the sampled conditions only. They do not measure or guarantee real-camera performance, and the zero-event bound applies only to the sampled synthetic condition distribution (independent seeded trials).

This file is generated by `npm run measure:geometry -- --plan` from `src/optical/testing/geometry-design.ts`. Its design parts are deterministic (no timestamps); the timing section is copied from `docs/optical/results/geometry-bench.json`, written by `--bench --write`. Results of the sweep are in `geometry-experiments.md` / `.json` (merge step: `npm run merge:geometry`).

## 1. What is simulated and what the reader gets

- Board: cards of 63.5 x 88.9 mm (module 1.5875 mm), rounded corners, laid out on a pitch of card size + gap, on a table of uniform gray, plus a 5 mm table margin. Raster: 2.520 px/mm (4 px per module, marker core 28 px), 4 x 4 anti-aliasing sub-samples. Image size 346 x 474 px (2x2) and 506 x 698 px (3x3).
- Camera chain, applied to the board raster in this order: in-plane rotation and perspective tilt (one projective warp, background = table gray, supersample 2), Gaussian blur, multiplicative lighting ramp. Each stage at zero strength is skipped, so the image is unchanged. Camera distance for the perspective factor: 1.0 image diagonals. The warp is about the image centre, which is the focus vertex of a 2x2 board; outer parts of the board can leave the frame at large rotation.
- Reader: `decodeGroup(image, { centerOffsetModules })`. The image is the only data input. The expected cards, positions and sum are used only afterwards, to score the result (`classify` in `geometry-trial.ts`). All recognition thresholds, tolerances, the acceptance radius (1), binarization (Otsu default) and the frozen codebook (SHA256 `515ECEB318648C14A47574496788236A2B1BBDFC7062387DB09303CB717CC2D4`) are untouched.
- **Reader layout parameter (decision for review).** The decoder's default expects marker centres 5.5 modules from the vertex (inset 1). For inset 1.5 and 2 the centres are 6.0 and 6.5 modules away. The reader is told the matching offset `inset + 1 + 3.5` (an existing option, `centerOffsetModules`; no threshold changes). To show that this is necessary, Tier 2 has two diagnostic cells that run inset 1.5 and 2 with the decoder defaults (an unrecorded 10-trial pilot: the defaults identified 10/10 at inset 1.5 and rejected 10/10 as INCOMPLETE_GROUP at inset 2). Without this option the inset sweep would measure the reader's built-in layout assumption instead of the card geometry. Decision needed: confirm that telling the reader the card layout is acceptable for the inset sweep.
- Scoring per trial: CORRECT = IDENTIFIED with the exact four cards and the exact Hidden_Sum. REJECTED = any other decoder kind (kinds tallied). FALSE_ACCEPT = IDENTIFIED with a wrong card set or sum, or IDENTIFIED when a card is absent. A 3x3 board is drawn so that exactly one interior vertex has four markers (rejection sampling on the distractor cards), so the ground-truth group is unique.
- Placement model: rows slide along their horizontal seams and columns along their vertical seams (the shift factor), every card rotates by its own seeded angle about its centre, and the gap factor is the only across-seam displacement. Where a rotated card runs into a neighbour, the later card in row-major order is painted on top (a raster convention, not a contact-mechanics model).
- Double-sided model: task 5.5 (`printLayers`, `observeFace`), extended to a whole board. The board rasterizer is tested to be pixel-identical to `observeFace` for one card and to `composeBoard` for FRONT boards. Registration and cut offsets are drawn per card (magnitude = level, direction random). Paper show-through is not simulated (Requirement 16.10 is a Milestone 8 measurement).

## 4. Tiered design

Reference geometries (Tiers 2 and 4): (r=3.175, inset 1), (r=3.175, inset 1.5), (r=3.175, inset 2), (r=0, inset 1), (r=6, inset 1), (r=6, inset 1.5). They are the baseline, its two inset improvement candidates (Requirement 15.7 step 1) and the boundary radii 0 and 6.0 mm.

Profiles (degradation levels, all taken from the factor levels above):

| Profile | Definition |
|---|---|
| CLEAN_DARK | flat, aligned, no camera effect, dark table |
| CLEAN_LIGHT | as CLEAN_DARK on a light table |
| MODERATE | shift 0.5 mm, rotation 1 deg, random camera rotation, tilt 10 deg, blur 0.5 px, lighting 0.2, dark table |
| STRESS | shift 1.0 mm, rotation 1 deg, gap 0.5 mm, random camera rotation, tilt 20 deg, blur 0.5 px, lighting 0.4, dark table |

Trials: 1000 for the four Tier 1 cells with the baseline geometry (r = 3.175 mm, inset 1), 200 for every other cell. Cells are never pooled.

Option, not applied: the task text asks for 1,000 trials for "the baseline cell". The plan reads that as the Tier 1 baseline cell of each profile. 55 further cells (Tiers 2-4) also use the baseline geometry; raising them to 1,000 trials would add 44,000 trials.

**Disclosure: how the profile levels were chosen.** The CLEAN / MODERATE / STRESS profile parameters were chosen after a small, unrecorded pilot on the baseline geometry (10 to 30 trials per variant, no log kept). STRESS was lowered to 1 deg per-card rotation and 0.5 px blur because the first draft (2 deg, 1.0 px) failed about 80% of baseline trials. The profile levels are therefore design choices made to put the reader in a region where it neither passes nor fails everything, not thresholds tuned until the reader passed. No recognition threshold, tolerance, acceptance radius or codebook value was changed at any point. The profile definitions were fixed before the sweep; no sweep result feeds back into them.

### Requirement 15.7 steps 2 and 3 (decision: not evaluated)

The decision table must evaluate steps 1-4 before it may recommend a corner-radius reduction. This plan evaluates step 1 (inset, Tier 1 and 2) and step 4 (alignment tolerances: placement errors in Tier 1/2, registration and cut in Tier 3). Step 2 (marker size and white margin) has no sweep in the task 5.6 text, and step 3 (detection and geometric-correction algorithm) is out of scope while the decoder is frozen. Decision taken for this task: steps 2 and 3 are NOT evaluated, so the decision table records them as such and does not recommend a radius reduction. The following Tier 5 was proposed and is NOT implemented: a Tier 5 on the reference geometries with module size {1.4, 1.5875, 2.0} mm x quiet margin {1, 1.5} modules under the CLEAN_DARK and STRESS profiles, about 6 x 6 x 200 = 7,200 trials; it needs `moduleMm` and `quietMarginModules` as cell parameters.

## 6. Statistics recorded per cell

For each cell, separately and never pooled: trials n; correct (all four cards and the sum) with rate; rejected with rate and a tally of the rejection kinds; false acceptances (wrong card set or sum returned as IDENTIFIED, or IDENTIFIED for an incomplete group) with rate; when the false-acceptance count is 0, the exact one-sided 95% upper bound 1 - 0.05^(1/n) (0.30% for n = 1000, 1.49% for n = 200); otherwise the count, the rate and all failing seeds instead of a bound; a tally of failure causes (decoder kind, plus a flag when the conservative containment bound of the cell's cards is violated); the first rejected seeds; `voidToBorderCornerMm` (true minimum distance from the Central_Void to the black-border corner; `null` in code and "No Central_Void" in the report for r = 0) and `voidTipToBorderCornerMm` as an additional reference column, with the containment clearance and validity of the geometry. For incomplete-group cells rejection is the expected outcome (correct = 0 by definition, `rejected` is the good count, a false acceptance is any IDENTIFIED result). Results carry the disclaimer text and no timestamps.

Seeds: `trialSeed(cellId, trialIndex)` = hash of (base seed 20260514, cell id, trial index), 32 bit. Cards, placement errors, duplex errors and camera draws use four independent streams derived from that seed. Trials within a cell are independent draws; cells are not paired.

## 8. How to run it

- Run per tier: `npm run measure:geometry -- --run --tier 1`, then 4, 2, 3 (Tier 3 is the largest). Each finished cell is written to `.geometry-work/tier<N>/<cell id>.json`; a restarted run skips cells that already have a file, so an interrupted run loses at most one cell.
- Concurrency: processes are independent and share nothing. Start k shards of a tier with `--shard i/k` (cells are dealt round-robin, so every shard gets a similar mix); each shard writes disjoint files. A merge step (Phase B) reads the cell files in cell-id order and writes `geometry-experiments.json` and `.md` plus the decision table; results do not depend on the shard layout or the number of processes because every trial seed depends only on (cell id, trial index).
- Smoke test before the real run: `--run --tier 1 --max-trials 5 --work-dir .geometry-smoke --cell r3.175-i1`.
- Phase B should also keep a verbatim copy of the console output of each tier run next to the results (`m5-6-*.txt`).
