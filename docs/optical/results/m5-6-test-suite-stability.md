# Test suite stability: the 5 s timeouts of the default configuration

SYNTHETIC-image test suite; this note is about the test runner only. Durations are wall-clock measurements on one machine (Intel Core i5-10400F, 6 cores / 12 logical processors, 40 GiB, Windows, Node v24.20.0, vitest 5.1.0) and are NOT deterministic; they are recorded here once, they are not regenerated by any script.

## Finding

The timeouts were CPU contention, not a functional defect. On an otherwise quiet machine the default configuration (`vitest --run`, 11 workers = logical processors - 1) passed all 431 tests in 3 of 3 runs. When the machine is saturated by other processes (the 8 sweep shards that were running at the time, the geometry analysis, the editor and other desktop applications), tests that have no explicit timeout and need 1.3 to 3.5 s of CPU on a quiet machine exceed vitest's default 5 s and fail with `Test timed out in 5000ms`. No assertion failed in any run; every failure below is a timeout.

Failing tests under load (all `Test timed out in 5000ms`, none of them has an explicit timeout): `detect.test.ts` "blurred non-integer scales" (in every loaded run, default and 4 workers), `render.test.ts` "renderMarker geometry modulePx 8", `physical-card.test.ts` "a rotated card is rotated about its centre" and "composer smoke check with decodeGroup", `detect.test.ts` "crisp integer modulePx 2..24", `decode-fragment.test.ts` "agreement with the exact enumeration" (12-spinner run), and, in one earlier 4-worker run under load, `physical-card.duplex.test.ts` "containment under registration and cut error ... zero error". These are the test names and files of the earlier reports (duplex test, detector blur test, `physical-card.test.ts`).

Running the suite with `--testTimeout=2500 --maxWorkers=4` on the quiet machine failed exactly two tests, "blurred non-integer scales" (3332 ms) and "a rotated card is rotated about its centre" (3061 ms); every other test without an explicit timeout finishes in under 2.5 s there.

## Machine and competing processes

12 logical processors. During the final verification an Android emulator process (`qemu-system-x86_64-headless`, 4 GB, started at 01:50:53, not part of this project) was using about 6.5 logical processors continuously; the two timeouts of that verification are the same two tests that fail first under any load. The emulator was already running during part of the session (its total CPU time at the end was 2276 s), so the "quiet" runs above are quiet only to the extent of the readings stated next. Before each quiet run the system CPU counter read 17 to 37% from other applications: the editor (one Kiro process used about 0.96 of a logical processor over a 10 s window), ChatGPT / Codex desktop processes and about 8 idle node processes running MCP servers (`mcp/server.mjs`, a few CPU seconds in total). Vitest itself starts 11 worker processes in the default configuration, so a default run on this machine uses 11 of 12 logical processors and leaves one for everything else.

## Recommendation

- Reliable invocation on a quiet machine: `npm run test:ci` (added to `package.json`: `vitest --run --maxWorkers=4`). 3 of 3 runs green, same wall time as the default (43 to 53 s), about 20 to 30% shorter single-test durations than with 11 workers, and one more free processor for the rest of the desktop. The plain `npm test` also passed 3 of 3 on the quiet machine.
- Limit of any worker setting: it does not protect against an externally saturated CPU. With the CPU saturated, both the default and the 4-worker run time out in the tests listed above. Do not run the suite while a sweep or the 45 degree analysis is running.
- Proposed, NOT applied (changes test source, needs a decision): give the six tests in the duration table an explicit timeout, for example `{ timeout: 30_000 }` as the last argument, as the 8 long tests already do (`LONG = 300_000` in `physical-card.duplex.test.ts`, 120 000 ms in `physical-card.test.ts`). This keeps every assertion and only removes the dependence on the machine load. A global `testTimeout` in `vitest.config.ts` was not proposed because it would also apply to tests that should stay fast.
